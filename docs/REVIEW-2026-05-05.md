# Codebase Review: ControlledChaos
**Date:** 2026-05-05
**Stack:** Next.js 16 (App Router, React 19, React Compiler), TypeScript strict, Tailwind v4 + shadcn, Drizzle/Neon, Convex (ephemeral only), Clerk, Claude Haiku, Groq, Web Push
**Project type:** Next.js PWA + standalone MCP server, Vercel-hosted

## Executive Summary

ControlledChaos is in solid mid-maturity shape — schema is thoughtful, the type system is clean (TS check passes, only 2 `any` casts in src), and the UI shell is well-considered for ND users (paper-mode palette, custom mobile dock, install-prompt handling, careful iOS PWA SW policy). The biggest risks are concentrated in two places: (1) the push-triggers cron is a 459-line serial loop over all users with no `maxDuration` export, which will start hitting Vercel timeouts as the user base grows, and (2) the MCP server, while broad, omits the app's actual core loop (`cc_recommend_next_task`) and uses raw SQL strings against a schema that the main app evolves through Drizzle — schema drift will silently break MCP tools (the recent "drop 4 dead columns" commit is exactly this risk class). Lint reports 23 errors that should be cleaned before next public push.

## High Priority Findings

### 1. Push-triggers cron has no execution-time guardrails
- **What**: `src/app/api/cron/push-triggers/route.ts` (459 lines) does a serial loop over every push-enabled user, awaiting AI message generation, location lookup, snapshot building, deadline/event/scheduled/medication/checkin/inactivity/crisis checks per user. Zero `export const maxDuration` or `export const runtime` declarations exist anywhere under `src/app/api`. Vercel default is 10s on Hobby and 60s on Pro.
- **Why it matters**: This will silently start truncating notifications mid-loop as users grow. Symptoms will be "user N gets notifications, user N+1 doesn't" with no obvious cause.
- **Suggested action**: (a) Add `export const maxDuration = 60` to the cron routes, (b) parallelize the per-user loop with `Promise.allSettled` chunked at ~10 concurrent users, (c) add a duration log at the end of the run for visibility.
- **Effort**: Half-day

### 2. MCP server is missing the app's core loop
- **What**: README markets the loop as "AI tells you what to do right now," and `/api/recommend` powers `DoThisNext` on the dashboard — but there's no `cc_recommend_next_task` MCP tool. From Claude Desktop, you can list/create/update tasks but you can't ask "what should I work on right now?" — the most natural ADHD-coaching question.
- **Why it matters**: This is the differentiating feature of the app. Exposing it to MCP turns Claude itself into an extension of the recommendation engine.
- **Suggested action**: Add `cc_recommend_next_task` (with optional `energy_level`, `time_available`, `location` params) that calls the same recommendation logic used by the web route. Also add `cc_get_active_crisis` so a Claude session can know when the user is in a crisis state.
- **Effort**: Half-day

### 3. MCP raw-SQL coupling to a Drizzle-managed schema
- **What**: `mcp/src/tools.ts` (2236 lines) writes raw SQL strings against tables that the main app evolves via Drizzle migrations. There's no shared types or schema source. Recent commit `706e4e2` ("drop 4 dead schema columns") is the exact failure mode — column rename/removal will produce silent runtime failures only when an MCP user happens to call the affected tool.
- **Why it matters**: As the schema continues to evolve toward launch, MCP tools will rot without anyone noticing until a user reports the failure.
- **Suggested action**: Either (a) import the Drizzle schema into the MCP server and use Drizzle's query builder there too, or (b) add a smoke test that runs each tool's `SELECT 1`-style probe against the live DB on CI. Option (a) is the durable fix.
- **Effort**: Multi-day for full Drizzle migration; half-day for smoke tests.

### 4. Lint reports 23 errors — including a React 19 effect bug
- **What**: `pnpm lint` returns 23 errors and 32 warnings. The most concerning: `src/hooks/use-voice-recorder.ts:40` violates `react-hooks/set-state-in-effect`, which under React Compiler can cause cascading re-renders on the brain-dump voice path — a hot user flow.
- **Why it matters**: TypeScript passes cleanly, so this is the only signal of real bugs and these are getting ignored. The voice-recorder issue is on a critical path.
- **Suggested action**: Run `pnpm lint --fix` for the auto-fixable subset (4 fixable per the report), then triage the remaining errors. Add lint to `prebuild` or a pre-commit hook so it stops drifting.
- **Effort**: Half-day to clean; quick fix to wire into pre-commit.

## Medium Priority Findings

### 5. `db.transaction()` in queries.ts vs CLAUDE.md guidance
- **What**: `src/lib/db/queries.ts:666` uses `db.transaction()` in `reorderTasks`, but CLAUDE.md asserts "Neon serverless driver does NOT support transactions." Drizzle's `neon-http` driver actually does support transactions for non-interactive batches (which `reorderTasks` is), but the rule and the code are now in conflict.
- **Why it matters**: The next time you (or Cody) hit a bug here, the CLAUDE.md rule will misdirect debugging. Either the rule is stale or the code is wrong.
- **Suggested action**: Test `reorderTasks` against a real Neon DB. If it works, update the project CLAUDE.md to clarify "neon-http supports non-interactive batched transactions only" and call out `reorderTasks` as the canonical pattern. If it fails, replace with sequential updates.
- **Effort**: Quick fix

### 6. `queries.ts` (3103 lines) and `tools.ts` (2236 lines) are navigational hazards
- **What**: A single file holds every DB query in the app. Same shape on the MCP side. Both are well-organized internally with `// =======` section headers, but search/jump performance and review-burden are real costs.
- **Why it matters**: Cognitive load when adding features; merge-conflict surface area; harder for a sub-agent to scope reads. ND users (you) will feel this more than average.
- **Suggested action**: Split by domain — `queries/tasks.ts`, `queries/calendar.ts`, `queries/crisis.ts`, etc., re-exported from a `queries/index.ts` barrel. Same shape for MCP tools. No behavior change.
- **Effort**: Half-day mechanical split.

### 7. Friends/Parallel Play has full backend but minimal UI surfacing
- **What**: Schema has `friendships`, `nudges`, `rooms`, `room_members`. APIs exist at `/api/friends/*`, `/api/rooms/*`, `/api/friends/nudge`. But `src/components/features/friends/` is empty — the only friend UI is `friends-settings.tsx` buried in settings. `parallel-play-spec.md` (dated 2026-04-29) is sitting untracked at the repo root, and recent commit `b4dc921` shipped "friends' rooms browse view." This area looks mid-build with significant gravity behind it.
- **Why it matters**: Either this is in-flight (spec sitting at the root suggests so) and the report should just confirm scope, or it's stalled and the partial wiring is risk. Settings → Friends is hard to discover; friends/nudges aren't a settings concern.
- **Suggested action**: Either commit `parallel-play-spec.md` into `docs/development guides/` and confirm the next milestone, or carve out a top-level `/friends` route so the feature is discoverable. Move `friends-settings.tsx` out of settings into a friends feature folder.
- **Effort**: Half-day for the route + relocation; spec scope is its own work.

### 8. Notification log table appears unused for retention or insight
- **What**: `notifications` table records every push/email sent but the only consumer is `NotificationBell` (last few items). There's no UI to see "what notifications did I get this week," no purge, and the table will grow unbounded.
- **Why it matters**: It's either useful telemetry the user can't see, or table growth waiting to happen. Pick one.
- **Suggested action**: Either (a) build a `/settings/notifications/history` view + a 30-day purge cron, or (b) drop the table and rely on the bell-only short-tail behavior.
- **Effort**: Half-day

## Low Priority / Nice-to-Have

### 9. ESLint config is minimal
- Just `eslint-config-next`. No `no-floating-promises`, no `no-unused-vars` enforcement (they exist as warnings — 32 of them). Adding a few targeted rules would catch a class of real bugs.
- **Effort**: Quick fix

### 10. Test coverage is concentrated in pure logic only
- 5 test files: timezone, energy, schedule, recap-assemble, crisis-moments. All `lib/__tests__/`. None of the AI prompt logic, none of the cron handlers, none of the recommendation pipeline. The pure-logic tests are good — coverage is not.
- **Suggested action**: Add tests for the AI parsing (`parseDump`, `recommendNextTask`) using fixture inputs, since these are the highest-risk surface. Don't aim for 80% coverage — aim for "AI changes won't silently regress."
- **Effort**: Multi-day; can be incremental.

### 11. `/api/dump/photo/extract` and `/parse` style splits
- Voice and photo dump endpoints split into `extract`/`transcribe` + `parse`. Worth checking if the two-call pattern adds latency over a single combined endpoint. Not a bug, just a design check before launch.

## Dimension Summaries

### UI/UX: 🟢 Solid — paper-mode palette, careful iOS PWA handling, ND-conscious shell
The dashboard is well-organized: Greeting → DoThisNext (single hero) → DailyMomentum + ScheduleMyDay strip → MicrotasksZone → collapsible TaskList. That's the right ND hierarchy — one loud surface, the rest deferred. AppShell handles install prompts (Android + iOS Safari), bottom mobile dock with moments-bar, command palette + keyboard shortcuts. Custom utility classes for the brand palette via CSS variables.

### Features: 🟡 Adequate — comprehensive but Friends/Parallel Play wiring is partial
60+ API routes spanning tasks, calendar (Canvas iCal), goals, dumps (text/voice/photo), recap, recommendations, crisis (manual + auto detection + chat), microtasks, medications, locations + commute times, friends/nudges, rooms, push, onboarding. The dump → parse → tasks loop is fully wired. The friends/parallel-play surface is the under-baked area (see #7).

### MCP: 🟡 Adequate — broad coverage but missing the core loop and schema-coupled
34 tools is generous coverage. Annotations are correct (readOnlyHint, destructiveHint, idempotentHint). Tool descriptions are detailed. Two real issues: (a) the recommendation engine is invisible to MCP — see #2, and (b) raw-SQL coupling to a moving schema — see #3.

### Architecture: 🟢 Solid — strict TS, clean schema, good module boundaries
TS strict; only 2 `any` casts in src. Schema is thoughtful (soft deletes, indices on hot paths, unique constraints on the right keys, `email LOWER` unique to prevent Clerk-rotation duplicates, `crisis_plans.dataHash` for staleness). The Convex/Drizzle split is principled: ephemeral presence in Convex, persistent membership in Drizzle. Cleanup commit `706e4e2` shows discipline.

### Infrastructure: 🟡 Adequate — push-triggers cron has scaling cliff
Vercel + Neon serverless + Cloudflare R2 + Resend, all standard. Cron schedule is sensible (15-min cadence, digest windows). Service worker is well-tuned for iOS PWA (no `skipWaiting`, no `clients.claim`, `updateViaCache:"none"`) — visible care from getting bitten before. The push-triggers concentration risk in #1 is the main gap.

### DX: 🟡 Adequate — TS clean, lint dirty, tests narrow
TS is clean. Lint is loud (23 errors, 32 warnings). Tests are narrow but high-quality. `pnpm db:push` for fast iteration, real migrations checked in. Multiple maintenance scripts for dedup/remap operations. `mcp/` and `convex/` properly excluded from main TS check. README and CLAUDE.md are both well-written and current.

## Strengths

- **Type safety discipline**: only 2 `any` casts in 264 src files, strict mode enforced, TS passes cleanly.
- **Schema as documentation**: every table has section headers, every soft-delete pattern is consistent, every index is justified by a query.
- **iOS PWA awareness**: the SW notes (`// no skipWaiting because iOS demotes window to Safari mid-session`) show real production pain has been worked through.
- **Brand discipline**: ADHDesigns palette is wired through CSS variables with semantic shadcn mapping rather than hardcoded hexes.
- **Operational honesty**: the email-conflict error references actual recovery scripts (`scripts/dedupe-users-by-email.ts`) — that's the kind of error message that saves a future debugging session.
- **Domain-modeled recommendation pipeline**: the user-snapshot → AI prompt → action separation in `lib/notifications/triggers.ts` and `lib/ai/` is the right shape; it just needs guardrails (#1) and MCP exposure (#2).
